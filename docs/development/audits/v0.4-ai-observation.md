# v0.4 提前开展的真实 AI 使用观察

> Audience: ToolX 维护者与后续实现者
> Status: Completed small qualitative observation; no adoption-cost claim
> Applies to: 2026-10-18；冻结 24466b2 二进制；并行 v0.4 开发
> Source of truth for: 首轮实际 AI 选择、额外核验、阻碍及其对实现优先级的影响

## 观察先于新能力选择

v0.4.x 的目标是降低 AI 完成实际自动化任务时的采用与信任成本。按照更新后的
[主线](../design/v0.4.x-mainline.md)，本轮在契约修复期间就进行观察，没有等待
配置解释原型，也没有把使用 ToolX 设为任务要求。

这轮只有一个真实项目边界、每条件一次尝试，用于发现阻碍。它不是性能基准、
完整 agent benchmark 或统计对照，不能证明采用成本下降。后续改善按实际问题
选择；配置来源解释仍未被选为必须实现的新能力。

## 材料与执行方式

任务来自此前真实 podkop/sing-box 消费需求的配置发布边界：四份生成/用户配置，
递归对象合并、后层标量优先、数组按序追加，保留两个本地 mixed 入站和两条规则，
诊断已有故障，实际验收后交付可复用脚本和 current.json，并检查真实无效配置与
发布失败时保留已接受文件。生成配置禁止修改，旧 current 不能算本次成功。

独立新上下文的 agent 获得相同 brief、输入、端口和成熟工具。

| 条件 | 可用材料 | 实际选择 |
| --- | --- | --- |
| A baseline | sing-box 1.12.12、Python 标准库、可用 deepmerge/jsonschema、PowerShell/rg | 先试原生 merge，再自写递归合并与项目 publisher |
| B available | A 的全部材料，加可选 toolx-sync 与四份现有规范 | 采用 ToolX 合成与发布，同时自写合并 reference 核对候选 |

没有提供先前实验的 recipe、故障位置或修复答案。两个 agent 禁止读取对方目录、
准备程序、之前审计或实现答案。任务准备与独立验收程序进入
[experiments/v04_ai_observation](../../../experiments/v04_ai_observation/README.md)。
模型可复用自己写出的脚本，也可拒绝 ToolX。A 选择自己实现 merge 是实际行为，
没有事后强迫它采用 deepmerge；先前成熟工具的强基线仍由配置切片提供。

## 实际结果与独立核查

两组都修复了 route.final 引用不存在的 gateway，且没有改生成文件。
它们分别留下 reusable publisher、原始命令/输出、实际运行记录、失败变体和
observation.json。两组均实际执行每入站 HTTP 与 SOCKS5，共四次本地行为请求，
并检查新实例/端口归属与清理。

维护侧进一步独立读取完整输出配置和原始生成文件摘要，调用原生 check，启动
发布文件并通过两个新实例拥有的入站访问本地 HTTP origin。两组均通过；清理后
该子进程的 listener 消失。独立 oracle 不把 agent 的完成自述当作产物证明。

| 证据 | A | B |
| --- | --- | --- |
| 递归对象、标量 debug 覆盖、两入站、两规则及顺序 | 通过 | 通过 |
| 独立 native check＋实际归属明确的代理请求 | 通过 | 通过 |
| 生成文件身份未变 | 通过 | 通过 |
| 实际无效配置不发布 | 原生拒绝错误 log level；旧目标保留 | 原生拒绝 unknown field；旧目标保留 |

## 观察到的阻碍

1. **选择与理解有实际成本。** A 先试原生 merge，实际发现它保留 warn，不满足
   后值 debug 覆盖。A 明确选择自写短 merge，以避免研究成熟库的默认语义。
   这不是成熟库做不到，而是该次模型的采用选择。
2. **采用 ToolX 仍可能造第二个轮子。** B 使用 ToolX，但 publisher 内保留独立
   Python merge，并把结果逐树比较；理由是额外信任检查。代码与原始动作均可
   核对，不能把“模型用了 ToolX”视作已经消除了自行实现或验证的成本。
3. **业务验收不能由本地 schema 替代。** 两组都观察到 check 放过不存在的默认
   出口，实际启动才失败；两组都补了项目 policy、运行和代理请求。B 拒绝把
   schemax 当完整项目 schema，没有要求 ToolX 接管这些职责。
4. **失败事实不足产生核验负担。** B 的发布错误 data 为空，无法据回执确定哪步
   写过、回滚是否成功，只能比较旧/新摘要。B 没有编造回滚序列。这项问题与
   已有高风险契约修复直接重合，新的 execution/rollback 字段有明确消费理由。
5. **副作用边界会造成错误测试假设。** B 原本想用空目录阻止 snapshot 写入，
   旧 ToolX 实际成功替换了目录；它保留失败注入的失效证据，再用普通文件父路径
   制造真实第二写失败。新版 AtomicWrite 明确拒绝目录/链接，避免该意外副作用。
6. **环境摩擦要单列。** 两组都曾在普通沙箱中遇到 loopback 限制，转授权执行后
   实际验证；A 另记录路径处理和命令引用修复，B 也记录错误失败 fixture。
   不把这些环境差异伪装为某工具的性能或能力差异。

这些是特定尝试的可观察事实，不是模型总体偏好，也不能通过命令数、脚本行数或
stdout 大小换算成 token 成本。尤其不能推断正确来源解释一定能消除上述负担。

## 对 0.4.0–0.4.1 的实际影响

0.4.0 继续修已证风险：错误 trace、失败 report 丢失、恢复误报、原子目标可见性，
并回归真实文件状态。正确 trace 只修已承诺的 layer 归因，不顺带发布文件解释 API。

0.4.1 的首项有界改善是缩短能力与验收边界的入口：新增
[automation guide](../../automation.md)，把合并选择、schema 限制、候选/验收/发布
分工、snapshot/dry-run 与失败解释放在一处，链接规范而不是增加另一套机器协议。
它回应的是本轮的选择、额外核验和副作用误解；尚未证明新资料减少了模型成本。

暂不新增配置解释、通用发布 API 或 runner。后续留出任务应观察：B 是否仍写同样的
shadow merge，失败回执是否少触发必要的定位查询，以及发现成本是否被短入口降低。
若阻碍转向其它职责，优先级随证据改变，不为了既定候选强行推进。

因此不能比较失败恢复成本的因果差异。没有时间/token 优势的统计结论。

只验证 Windows 本地 JSON 边界、无外网；域名 regex 获原生接受并保留，但没有触发
域名匹配，未验证 OpenWrt、热 reload、并发发布、断电或其它项目。下一轮需要留出
任务与更多尝试，而不是把本轮两个完成结果当作新架构的证明。
