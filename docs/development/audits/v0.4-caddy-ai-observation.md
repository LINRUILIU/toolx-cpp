## 真实任务与附加压力测试分开解释

任务基础来自 [Caddy #6770](https://github.com/caddyserver/caddy/issues/6770)：
使用原生 JSON/API 维护多 host、带 ID 的路由，在 SPA fallback 前增加或调整 API
子路由。该条目是关闭为 not planned 的支持问题，不是本轮修复的 upstream bug。
实验将站点与源站改为回环，使用实际 Caddy 2.10.2，保持 API 反代、SPA 深链、
另一 host 与全部 route ID，以实际请求验收。生成配置不可修改。

Caddy 有自己的 [validate](https://caddyserver.com/docs/command-line) 和
[配置 API](https://caddyserver.com/docs/api)，模型可以选择它们。ToolX 不接管原生
模块初始化、HTTP 行为或服务 reload。原生验证不能证明 API 没被 fallback 截获，
因此 HTTP 验收是项目必要工作，不是额外的 ToolX 信任检查。

为复查文件契约，额外加入三份 JSON 的明确层顺序/数组替换 policy、两个相同
accepted 文件、真实第二目标锁定与旧候选负例。这些是共同契约压力测试，不是
原 issue 的自然要求；不能靠压力测试的收益宣称 ToolX 优于 Caddy 原生配置更新。

## 公平条件与观察边界

原计划三个新上下文依次执行 mature、fixed、released；允许尝试内调试与脚本复用。
相同项目输入、端口、缓存中的 deepmerge/jsonschema、Caddy、
origin fixture、脚本参数、回执记录要求与许可范围。两个 ToolX 条件均可不用它。
只有工具及对应资料不同；fixed 有当前短入口，因此观察的是代码/资料组合。

模型没有得到 publisher、旧任务答案或故障位置，不能读取 sibling、准备/验收器、
先前审计或 oracle 自检 publisher。后者仅用来证明验收器不会把“所有调用都失败”
误判为可靠恢复，保留于隔离自检目录，未提供给任一条件。

源码在 [experiments/v04_caddy_observation](../../../experiments/v04_caddy_observation/README.md)。
材料、二进制/文档 hash 和顺序在 `temp/v041-ai-caddy-20261018/predeclared.json`；
`frozen-verification.json` 保存当时已闭合门禁。各次实际脚本、命令与产物保留在
各自目录，独立 oracle 在其外。并行追加 Clang 检查占用 CPU，因此不比较耗时。

宿主模型具体 ID、完整 transcript 和 token 统计不可用。动作记录来自模型，但须
对照实际代码、原始输出与产物；不能把少几条命令、源码长度或输出字节换算成
模型成本，也不把一个项目的变化归因于与前一 sing-box 项目不同的二进制。

### 隔离偏差与重做

原 fixed 尝试在首次实现之前调用团队列表，工具返回了 mature 的完成摘要。该摘要
包含成熟方案选择与已通过的结果；虽然没有读取方案代码，仍可能影响后续选择，
不能算公平的独立对照。维护侧最初误判暴露在最终验证后，核对完整相对时间线后
立即更正。原尝试、失败、修复、子代理 review 和原始 evidence 全部保留，并通过
共同 oracle 核验其实际正确性，但不用于采用成本的主要比较。

另派一个新上下文 fixed_clean，逐项确认输入、guide 和 binary SHA256 与最初冻结
材料相同，不给它原尝试或成熟组摘要。规则明确禁止团队状态/摘要读取；需要子
review 时可直接传入自身材料而不列举其它任务。实际执行顺序和原计划的偏差存于
`protocol-deviation.json`。本轮因此有四次父代理尝试，主要比较 mature、fixed_clean、
released；不能隐去多出来的观察成本，也不能声称严格的随机盲测。

## 共同独立验收

验收器先检查完整配置值、route ID、两个输出准确字节与生成/环境输入 hash，再用
新启动且 PID 对应的 Caddy/origin 发四次 HTTP 请求。源站日志必须证明收到
`/api/ping`，防止静态响应伪装为反代；结束后拥有的 listener 必须消失。

随后实际调用模型生成的 reusable entry：异输入/异输出正常对照；DEBUG 不同候选
先解锁发布、完整配置和 native/HTTP 验收；原生非法候选；成功后 malformed 输入；
同一 DEBUG 候选在第二目标真实锁定时发布。锁定有独立 OS replacement 探针，候选
需与解锁时的准确 hash 相同。只有非零退出、旧文件保留、阶段/候选/原始诊断均
相互佐证才通过；证据不够是 inconclusive，不能包装为成功 rollback。

回执和 evidence 环境变量是所有组相同的观察仪器，不是新的 ToolX 公共协议。
它们不是 syscall trace；一个安全的预检失败与实际完成首写后回滚要分别记录。

## 成本分类口径

项目必需工作包括 Caddy validate/HTTP、ID 与输入保护、候选身份、按要求验收
失败后两文件是否保留。额外核验只计为相信 merge/publisher 本身而增加的检查，
例如独立重写 merge 核对工具结果或另造通用语义夹具。按目的分类，不能照搬模型
把所有 hash/readback 都算“额外信任检查”的自述。

项目输入修复、publisher/验收代码修复、失败探索与重跑分别保留。观察者的共同
验收成本另列，不计成任何一组模型自己付出的核验，也不把观察仪器代码算作
ToolX 减掉的产品代码。

## 实际结果

三个有效条件均通过共同 oracle，原隔离失效尝试也通过正确性核验。各条件最终
默认发布输出为同一 2311 字节配置，SHA256
`22ac5bee6b6f96e2e12b561f88454d2c1327c5992ba2b3defb523f55ae22fea7`。
原生成文件 SHA256 始终为
`b021d57793f2cf91cb1a89dbd9af1d8dc2809b9a32275b405b0930e30209fb1b`。

| 条件 | 实际选择与发现 | 模型生成 entry 的调用记录 | 修复与重跑 |
| --- | --- | --- | --- |
| mature | cached deepmerge＋Caddy＋Python 发布 | 两轮各 7 次，共 14 次 | 首轮全过；调整 harness 的重复执行/evidence 保留后再跑 7 次；一次猜错输入文件名的读取 |
| fixed_clean | 读 CLI 与 automation 资料后未调用 ToolX；cached deepmerge＋Caddy＋Python 发布 | 首次成功 1 次、首轮 suite 5 次、最终 suite 6 次、receipt 回归 2 次，共 14 次 | 一次 scoped 静态 review；修正 receipt/参数诊断/独立清理三个 recipe 问题；harness 把真实错误限为 32，改为接受实际 5 或 32，完整重跑；一次猜错 evidence 路径的读取 |
| released | 读 CLI 资料后未调用 ToolX；stdlib 小型 merge＋Caddy＋Python 发布 | 原始错序拒绝 1 次，两轮 suite 各 6 次，共 13 次 | 一次 scoped 静态 review；修正 evidence I/O 中断清理及 resolve 后才检查 symlink，补强 readiness/receipt；同样修正 WinError 32 的错误断言并重跑 |
| fixed（仅保留，不参与主要比较） | 已见 mature 摘要；未调用 ToolX，使用 deepmerge | 14 次，保留在原 observation/evidence | baseline/完整 suite 各两轮；修复初始 HTTP 探针、OS 原始诊断和 storage 环境隔离；一次 scoped review；不从观察成本中删除 |

调用数仅描述保留的模型 entry 调用，不是模型成本分数。每次父尝试均允许自行
增加 review；实际 mature 没有使用，另外三次各使用一次。没有完整 transcript，
不能用这些数量推算 token 或认定修复版比旧版更贵/更便宜。共同 oracle 另外对每次
尝试调用 entry 五次（两个有效不同候选与三个负例），并独立启动 Caddy/origin；
这些是观察者验收成本，不计入表中的模型调用。

三组都只修了站点输入中的 API/SPA 顺序，保留所有 route ID、host 和生成输入。
旧版组先实跑原错误输入：native validate 成功而 `/api/ping` 返回 SPA，明确到
acceptance 阶段才拒绝；这证明原生语法/模块检查不能代替真实行为验收。
共同非法模块在 validation 阶段拒绝；后续 malformed JSON 在 compose 阶段拒绝且
candidate hash 为 null，不能把旧输出算成本次成功。

真实无 delete-sharing 的第二目标锁定返回 WinError 5，独立 OS 探针同样被阻止。
三个有效条件均记录第一目标已替换、第二目标失败并恢复第一目标，两个旧文件
保持准确字节；共同 oracle 还先用完全相同的 DEBUG 候选解锁成功，排除“未到发布
就拒绝”的假通过。错误码断言失败属于项目 harness 的错误假设，不能记为 ToolX
故障；原始失败保留，修正后的 suite 与独立 oracle 分别保留。

### 额外核验有没有减少

本轮没有可测得的 ToolX 特有核验减少，因为三个有效条件均未执行 ToolX。
fixed_clean 的理由是明确 merge policy 可由现成库完成，sync 重新合成输入，不能
直接消费已经验收的准确候选；增加它仍需保留 Caddy 验收和项目发布代码。released
认为一个小型 stdlib merge 足够审阅。选择理由与最终代码相符，但不能由模型自述
推导所有环境下的净收益；本轮的 Python 库和二进制均已缓存，没有冷安装比较。

成熟方案也有自身信任检查。mature 额外建立一个通用 deepmerge 策略夹具，验证
递归、数组替换、scalar/type conflict，并在两轮 harness 中执行；fixed_clean 的
alternate 输入还覆盖空数组和 object→scalar→object；released 用 alternate 输入
核对通用合并结果。每组一个独立的 synthetic merge 夹具组，均执行两次；后两组
嵌在必需的 alternate 参数验收中，不能把整个 native 调用重复计为额外成本。
它们都没有再写一套完整 shadow merge 作为独立 oracle。
相比首轮 sing-box 未出现 shadow merge 是事实，但任务、工具选择与实现都变了，
不能将其归因于修复。

三个脚本的原生验证/HTTP、route ID、输入保护、alternate 参数、重复执行和
旧文件 readback/rollback 属于明确的消费任务要求。模型在 observation 中把其中
某些项标为 extra trust，本报告按目的重分类，不把整段验收从 ToolX 核验成本里
虚减。fixed_clean 的两项 receipt 回归验证的是审查发现的项目脚本/观察仪器缺口；
这也是实际维护成本，但不是对 ToolX 的额外不信任。

还有不能忽略的项目侧差异：fixed_clean 额外读取 live `/config/` 9 次、`/id/…`
28 次核对加载值和 ID，brief 并未指定这些 API 方法。三个条件 native validator
分别调用 12/11/11 次，owned runtime pair 为 10/9/9；version 调用为 1/11/2。
这些数字体现 recipe 的验证选择与冗余，不能证明 ToolX 修复的效果。各脚本对
readiness/失败 HTTP 的记录粒度不同，不汇总成完整网络成本排名。完整核对口径
与执行数保存在归档的 `cost-classification.json`；文档读取和部分 review/死路仍
只有动作摘要，不伪造完整原始 transcript。

### 证据与观察器成本

原始脚本和调用入口分别为 `mature/checks.py`、`fixed_clean/verify.py`、
`released/acceptance_checks.py`，每组的 `publish.py` 接收三个共同参数。
`observation.json` 记动作和选择，evidence 留候选、native argv/exit/stdout/stderr、
HTTP、publication 与最终 receipt；最终配置在各自 `release/`。独立结果在
`independent-oracle/{mature,fixed,fixed_clean,released}/initial/result.json`，均为 passed。
归档入口 `collect.py` 保留失败尝试、文档、门禁与逐文件 SHA256 manifest，并校验 ZIP
内每个文件与 manifest 一致；本轮实物为
`temp/v041-ai-caddy-20261018/caddy-observation.zip`。

观察器本身也经历修复：最初自检发现 reject-all entry 可能通过只有负例的判断，
遂加入不同有效候选的正常对照、准确 hash 和完整 native/HTTP 验收。该自检源码/
失败与后续结果保留于 `temp/v041-observation-review`，未提供给模型条件。隔离重做、
观察器硬化、平台批准和材料归档都是真实研究成本，不能算成任何方案减少的产品
职责；本轮也不是严格盲测或模型性能排名。

## 对 v0.4.x 的收敛

契约修复继续交付，因为它们修正可复现的错误事实与数据风险；本轮实际 AI 观察
未证明额外核验或修复成本下降，正确性门禁不能替代采用收益证明。当前主线保持
轻量：0.4.0 收口既有修复及剩余正式发行门禁，0.4.1 保留资料/recipe 改善，不增加
新的公共操作。没有证据把配置来源解释提为前置条件，也不立项 runner。

“sync 不直接发布已经验收的字节”是观察到的边界，但 native API/OS 发布已可用，
双文件要求又是附加压力条件，所以本轮不据此新增发布产品。下一次能力立项须在
独立消费任务中先证明成熟方案无法合理减少某项反复承担的职责；冷接入、文件
来源诊断或其它已有操作均可成为观察对象，不能为促成 ToolX 使用而安排答案流程。
