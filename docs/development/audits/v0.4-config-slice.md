# v0.4 配置分层、验证与发布切片

> Audience: ToolX 维护者与后续实现者
> Status: Completed Windows experiment; no runner or product implementation
> Applies to: 24466b2 的新构建；sing-box 1.12.12；2026-10-18
> Source of truth for: 第二个独立消费任务的公平比较、实际证据与路线决策

## 决策

本任务中，现有 ToolX 能完成配置候选合成和有限规则校验，但未建立独特的任务收益。
成熟原生工具和成熟 Python 库能达到相同正确性，ToolX 没有减少业务验收、最终发布
保护或修复重跑。后值覆盖、数组替换等通用语义相对 sing-box 有差异，但成熟 merge
库也具备；不能仅凭原生工具语义不同就宣称 ToolX 优势。

当前继续保持轻量，不做 runner，也不新增受控发布协议。v0.4.x 按风险修复具体
契约缺陷，同时提前进行小规模真实 AI 使用观察，按实际阻碍选择后续改善。
准确来源诊断仍是一项候选，不作为模型采用验证的前置条件。
没有证据前，不把“合成＋校验＋发布”包装为已成立的新产品主线。

## 真实任务与范围

[podkop issue #280](https://github.com/itdoginfo/podkop/issues/280)记录了实际消费需求：
向生成的 sing-box 主配置加入用户维护的入站和路由规则，共用一个实例，并在检查后
按变更发布。用户提供过原生 merge/check、摘要比较和替换的保存方案；该请求关闭为
not planned，不表示上游采纳。

完整 podkop 依赖 OpenWrt/UCI。本轮重现它消费 sing-box 的 **JSON 合成与发布边界**，
并非路由器部署：一个生成配置、三个附加文件，合成两个仅监听回环的 mixed inbound、
一个 direct outbound 和一条用户规则。本地 HTTP origin 提供实际代理验收，不使用
TUN、外部代理、外网请求或系统代理修改。输入是依据真实格式构造的最小代表配置，
不是完整搬运用户的路由器配置，也不是已执行一个上游工单修复。

## 方案与公平条件

| 方案 | 候选合成与局部 policy | 业务验收与最终发布 |
| --- | --- | --- |
| A：项目原生工具＋recipe | sing-box merge；jsonschema 4.26.0 | 相同 native check、实际启动/代理请求、共享发布保护 |
| B：成熟库＋recipe | deepmerge 2.0；jsonschema 4.26.0 | 与 A 相同 |
| C：薄 ToolX 操作＋recipe | 当前 HEAD 的 toolx-sync，append arrays＋schemax 子集 | 与 A 相同 |

三个方案获得完全相同的四份输入、端口、规则、顺序、失败变体和修复答案。
脚本、二进制、端口分配及项目知识均可重复复用；没有只向 C 提供预写流程。
B 直接调用成熟 Merger，不手写递归合并。A 使用项目自带 typed merge，不以脆弱脚本
代替现有能力。比较各后端已经接入的重复任务，不是三个独立模型的盲测。

预登记和每次冻结输入保存在结果目录。主任务没有相互冲突的标量，以符合实际“增加
入站与规则”的需求；全局 append 保持路由数组顺序。标量冲突、空数组、null、类型
冲突和重复 tag 另用 61 次探针公开比较，不能把本任务结果泛化为任意配置等价。

共同 recipe 负责：冻结输入；生成私有 candidate；局部 policy；native check；启动
实际 sing-box 并通过两个入站访问本地 origin；核对输入、候选和目标摘要；同目录
准备文件和 os.replace；相同字节跳过发布。候选与最终文件字节必须一致。
原始 CLI 回执中的 published 仅表示写好了私有候选，不是整个业务任务成功。

没有再次运行 sync 重新合成后发布：那会重新读取输入，不能证明发布的是先前验过的
内容。最终发布保护属于共享 recipe，不能归为 ToolX 功劳。单次摘要检查不是原子 CAS；
本实验拥有独占目标，不承诺并发发布仲裁或断电持久性。

## 39 个场景的实际结果

三组各 13 项，共 **39/39 独立 oracle 通过**。每组 2 次发布、1 次 unchanged、
10 次按预期拒绝。通过表示符合预登记的成功或拒绝结果，不是 39 次业务成功。

| 场景 | 实际触发及验收 | A / B / C |
| --- | --- | --- |
| normal | 两入站均实际代理成功；发布字节等于已验候选 | published / published / published |
| repeat | 相同输入重新验收，目标相同，不替换 | unchanged / unchanged / unchanged |
| type_failure | listen_port 改成字符串 | 原生 decode / jsonschema / schemax 拒绝 |
| policy_failure | listen 改为业务合法但违反回环 policy 的 0.0.0.0 | 三组在局部 policy 阶段拒绝 |
| native_failure | 路由 domain_regex 为 `[`，实际 regex 编译失败 | 三组 native check 拒绝 |
| startup_failure | route.final 引用不存在的 outbound | 三组 check 通过，实际启动失败 |
| occupied_inbound | 父进程真实占用预期入站端口 | 三组实际启动失败；旧 listener 不计成功 |
| stale_candidate | 存在上次有效候选，同时新输入违反 policy | 三组拒绝，旧候选不计本次成功 |
| candidate_changed | 验收后向候选追加空白，字节身份变化 | 三组发布 guard 拒绝 |
| input_changed | 验收后修改原始输入字节 | 三组发布 guard 拒绝 |
| target_changed | 验收后另一个写入者修改 current | 三组不覆盖其内容 |
| publish_io_failure | Windows 真实打开 current 且不允许共享删除 | 三组 os.replace PermissionError；旧目标保留，候选/prepared 身份正确 |
| repair | 恢复实际 startup_failure 输入，rg 定位，编辑一个文件，再跑同一 recipe | 三组实际发布成功 |

`sing-box check` 的不足由实际运行暴露：missing-outbound 通过 check，run 才报告
default outbound not found。固定版本的 [check 实现](https://github.com/SagerNet/sing-box/blob/v1.12.12/cmd/sing-box/cmd_check.go)
只构造后关闭，未 Start；实验不能用 schema/check 成功代替运行验收。

oracle 独立读取当前文件与故障前内容，验证完整任务配置；仅规范化原生省略的 false
默认值、route action 默认值和单项字符串数组。它再次检查并运行发布文件，核对 TCP
listener 的实际 PID 属于新子进程，两个入站返回预期 origin 内容，退出后该 PID 的
listener 消失。负例要求指定失败阶段和确切漂移原因，不能任意早退也算通过。

## 成本与收益归因

| 可观察成本 | A 原生 | B 成熟库 | C ToolX |
| --- | --- | --- | --- |
| 正常 recipe 外部进程 | 3 | 2 | 3 |
| 正常额外 oracle 进程 | 2 | 2 | 2 |
| 13 场景 recipe 进程总数 | 32 | 19 | 32 |
| 成功场景 oracle 进程总数 | 6 | 6 | 6 |
| 原生 check＋启动/代理验收 | 都需要 | 都需要 | 都需要 |
| 输入/候选/目标摘要及最终替换保护 | 共享 | 共享 | 共享 |
| 修复操作 | 1 次 rg＋1 文件编辑＋1 次 recipe 重跑 | 相同 | 相同 |
| 正常 recipe 原始子进程输出 | 85 bytes | 0 bytes | 2,341 bytes |

外部进程不包含父 harness、Python 库调用和 socket 请求。B 的 merge/policy 在进程内；
0 bytes 不意味着没有日志或无需理解，policy 异常保存在 receipt。原始输出量有不同
捕获渠道，不能换算为模型 token 或“信任成本”。正常单次 recipe 耗时分别约
0.343/0.307/0.302 秒，未做随机顺序和统计重复，不作性能结论。

修复是双方共有的预写诊断和已知修复答案，实际执行了查找、编辑与重跑，**不是自由
定位试验**；不能据此宣称来源追踪节省了模型排错。业务资料、故障注入和答案对称。
安装成本也没有免费隐藏：所有方案都需要 sing-box；B 增加成熟 merge 库，C 增加
ToolX；本轮采用成本按已经可复用的环境观察。没有执行冷启动模型实验。

C 的窄便利是一次 CLI 集中提供通用层合成、有限 policy 和候选写入；对于无需 Python
的消费环境可能有接入价值。本轮 Python 环境中，B 的后端只需调用现成 Merger 和
validator，C 没有删除共同 recipe 的核心职责，因此不能据此建立独特收益。

已证实的有效改进来自流程研究：区分 check 与 Start、冻结候选、绑定发布字节、
防止旧服务/旧产物冒充本次结果。A/B/C 均得到这些能力，功劳归共同流程。

## 现有 ToolX 契约的实际缺口

HEAD 新构建的独立探针与源码核对显示：

1. **来源追踪不能作为修复依据。** overlays 被先合并成 local，trace 不含具体文件。
   数组替换、对象→标量留下消失路径；append 时未偏移下标。即使候选正确，trace
   也可能错误。失败 schema 不返回 trace，不能把“有 JSON 来源字段”当可信诊断。
2. **有限 schema 有额外适配成本。** 仅加入合法 `$schema` dialect 声明就被拒绝；
   不可直接消费普通完整 JSON Schema。不能为了这项任务复制整个 sing-box schema，
   应继续使用原生 validator。
3. **已有检查与发布没有字节绑定。** 实际 native check 有效 candidate 后修改其
   port 为字符串，再 sync --base candidate --out current，sync 成功，而 native
   check(current) 失败。它没有接受 expected digest 的契约；这不是违反未提供的 schema，
   但说明不能承接“之前验过了，所以可以发布”的责任。
4. **多写失败会丢失恢复事实。** out 写后，snapshot 的父路径是普通文件，产生真实
   I/O 失败；out 恢复，但 sync 失败 data 为空，必须额外读取文件才能确认。snapshot
   是本次新内容副本，不是旧内容备份；dry-run 成功也不证明目标可写。
5. **更新既有路径存在可见性间隙。** fsx 当前先把 target 移到 backup，再把新文件
   移到 target，参见 [write_file_atomic](../../../src/fsx.cpp)。单 writer、独立 reader
   的 HEAD 实跑观察到了 target 暂时 FileNotFound；同目录 os.replace 对照未观察到。
   不能把当前 atomic_write 名称解释为读者始终看到 old-or-new，也不能解释为多文件事务。
   正式独立探针中 40 次成功 sync 写入、1,537 次 stat 观察含 107 次缺失；40 次
   os.replace、320 次 stat 观察无缺失。两组单 writer、相同继承目录权限，无分享锁。

这些探针属于产品可靠性前置缺陷，未混进三方案的最终发布结果：C 只写私有候选，
最终采用共同 os.replace。轮询观察次数不是可靠性概率或平台普遍结论；POSIX、断电
和并发 writer 未在本轮测试。详见 probe_contract.py 及保留的完整输出。

## 合并语义与成熟竞争方案

[probe_merge.py](../../../experiments/v04_config_slice/probe_merge.py)在当前 HEAD 与
固定 native 二进制上跑了 61 次调用，53 次 exit 0、8 次预期 native 拒绝。

| 边界 | sing-box 原生 | ToolX |
| --- | --- | --- |
| 标量冲突 | 按完整路径排序，前值优先；逆转 -c 不改变 | 按 base/overlay 顺序，后值优先 |
| 数组及空数组 | append，空数组不清除 | append 相同；默认 replace 可以清除 |
| 对象＋后层 null | 可拒绝合并 | null 覆盖 |
| 输入类型错误，即使后来覆盖 | 逐层 typed decode 拒绝 | 通用合成可成功，另需 policy/原生验收 |
| 重复 inbound tag | merge 已拒绝 | append 可产生重复项，需后续原生检查 |
| 默认字段、单项列表 | typed 输出规范化 | 保留通用 JSON 形状 |

反转文件名以取得后值优先会同时反转路由数组顺序，不能视为零成本通用适配。
固定 [readConfig 实现](https://github.com/SagerNet/sing-box/blob/v1.12.12/cmd/sing-box/cmd_run.go)
和 [merge 实现](https://github.com/SagerNet/sing/blob/v0.7.13/common/json/badjson/merge.go)
支持上述观察。需要通用覆盖时，成熟 [deepmerge](https://deepmerge.readthedocs.io/)
也能选择对象 merge、列表 append/override 和冲突 override；本实验已实际使用 append
Merger 路径。没有证明 ToolX 独占这种能力，更没有与所有成熟配置系统作全面比较。

## 有效性限制与后续门槛

探索 v1 中原生配置真实运行成功，但严格 JSON oracle 把省略默认 action 判成失败；
因此补了有界语义规范化，再正式运行三组，并增加真实占用端口负例与 PID 核对。
保留探索证据，不把 oracle 修正算作某后端修复收益。最终使用 comparison-v3，未选择
性排除失败场景。

只测 Windows、本地四文件、无冲突追加任务。未测模型自由采用、token、冷安装、
大配置性能、完整 podkop、热 reload 或跨平台发布。可靠性缺口不是所有消费者都需要
ToolX 来修复的证据，修好缺陷也不自动创造产品优势。

“准确文件来源＋明确数组策略＋失败仍可用的诊断”是一项待验证候选，以成熟配置
系统或带来源的短脚本为对照。可与实际 AI 使用观察并行，不优先于观察中出现的
其它阻碍。必须在未预写定位答案的真实故障中减少读取/额外检查，且同等正确性。
做不到就继续复用成熟 recipe，不扩展进程层、发布事务或统一协议。
版本安排见[收敛后的主线](../design/v0.4.x-mainline.md)。
