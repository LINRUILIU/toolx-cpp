# ToolX v0.4 真实任务验证切片

> Audience: ToolX 维护者与产品方向评审者
> Status: Completed deterministic validation; runner benefit not established
> Applies to: 2026-10-18 Windows 单项目验证；正式数据 comparison-v3
> Source of truth for: 三方案的实际结果、成本归因与对 v0.4.x 规划的调整

## 结论

本轮没有建立统一 runner 相对薄方案的新增正确性或修复收益。成熟工具与可复用
项目脚本、薄 ToolX 打包操作、最小统一原型，在同等输入和验收下均满足 9 个场景。
27 次运行中，15 次正常或修复运行成功，12 次负例按要求失败；正式结果没有错误通过。

本任务的主要收益来自项目流程与验收改进：真实测试失败停止交付、候选包消费后
才发布、旧包不冒充本次结果，以及真正使用包内头文件和库。统一原型增加了集中
产物引用校验和逐步记录，但未减少验收、修复动作或重跑步骤。

因此撤回“统一 runner 已是 v0.4.x 主线”的预设。当前采用成熟 recipe 主导的
轻量方向；ToolX 的单操作优势仍需在具体职责上证明，本轮也不足以支持立即发布
新的 verified-package 产品。统一核心保留为候选，后续需求可以重新提供证据。

## 独立项目与重复任务

项目是 [TinyXML2 10.0.0](https://github.com/leethomason/tinyxml2/releases/tag/10.0.0)，
固定 commit 为 `321ea883b7190d4e85cae5512a12e5eaa8f8731f`。
上游已有静态 Release 的 build、CTest、install 和安装后 find_package 消费测试，
对应 [固定版本 CI](https://github.com/leethomason/tinyxml2/blob/10.0.0/.github/workflows/test.yml)。

验证任务是重复生成可消费的静态 SDK：

```text
固定项目输入 → configure/build → 上游 CTest → 本次 install tree
→ 候选 tar → 独立前缀解包 → 消费项目编译与完整上游测试 → 发布正式 tar
```

tar 交付与本次结果关联是本轮补充的流程；构建、测试、安装和消费基础来自上游。
任务没有要求替代 CMake/CTest，也没有让 ToolX 获得一份对照组没有的业务答案。

环境是 Windows、MSVC 19.51、Visual Studio 18 2026 generator、CMake 4.2.3、
Python 3.13.9。ToolX 使用已有本地 toolx-pack 构建，记录其完整 SHA-256；
没有把它当作重新构建或认证的发行包。没有三平台或模型采用成本结论。

## 三个竞争方案

| 方案 | 项目编排 | 打包后端 | 额外职责 |
| --- | --- | --- | --- |
| A 成熟方案 | 可复用 Python recipe，调用上游 CMake/CTest | shutil.copytree 与 cmake -E tar | 与其他方案相同的内容验证、回执和发布 gate |
| B 薄 ToolX | 与 A 相同的 recipe | 分开的 toolx-pack stage/archive | 单操作包住阶段状态、候选归档、内容核对和发布；不接管整个项目流程 |
| C 最小统一原型 | 同一 recipe 放入有限顺序 runner | 与 B 完全相同 | 集中检查具名产物引用，写 intent/observation 增量日志，失败后跳过后续步骤 |

三者共享同一个 project_steps 定义、测试输入、缓存政策、包内容检查和外部结果
验收。A 也有失败停止、当前产物 hash、JSON 结果和旧产物保留，未被削弱为脆弱脚本。
源输入按固定 tracked 文件清单计算内容身份，避免测试生成文件污染输入指纹；
每个场景三者的输入摘要均相等。方案顺序按场景轮换。

每个方案建立自己的上游构建缓存，首次正常运行冷构建，后续复用。消费项目使用
本次独立前缀和新构建目录，三者条件一致。修复期间也允许同等复用脚本与缓存。

## 场景与实际结果

| 场景 | 实际操作与独立判定 | A | B | C |
| --- | --- | --- | --- | --- |
| normal | 构建测试通过，tar 与本次 install 文件内容一致，独立消费通过 | 成功 | 成功 | 成功 |
| test_failure | 合法 XML fixture 中 amends 改为 regressions，触发上游 4 个原有断言；无旧目标包 | 正确失败 | 正确失败 | 正确失败 |
| stale_archive | 保留上次成功包，当前上游测试仍失败；旧包不计本次成功 | 正确失败 | 正确失败 | 正确失败 |
| repair_test | 实际恢复 fixture 文本，复用构建缓存，全流程重跑 | 成功 | 成功 | 成功 |
| partial_archive | 完成 stage 后，将归档输出路径预创建为目录，触发真实 I/O 失败 | 正确失败 | 正确失败 | 正确失败 |
| repair_archive | 新运行采用干净输出位置，保留前次失败目录并完整重跑 | 成功 | 成功 | 成功 |
| consumer_failure | 候选包生成后损坏解包头文件，触发真实消费编译错误；不替换旧正式包 | 正确失败 | 正确失败 | 正确失败 |
| repair_consumer | 新运行解包未损坏内容，完整重跑并发布 | 成功 | 成功 | 成功 |
| warm_repeat | 不改输入，使用相同缓存政策重复整个任务 | 成功 | 成功 | 成功 |

归档失败保留 stage，回执明确 stage succeeded、archive failed、后续 skipped。
消费失败保留已验证候选包，正式发布步骤 skipped。失败时 current_artifact 为 null，
旧正式包摘要保持不变。这里没有把失败说成全局回滚，也没有把旧包保留当作错误。

真实测试失败来自受控 fixture 回归，未修改测试断言或伪造 exit 1；不是复现一个
历史 GitHub issue。消费失败也由编译器实际发现损坏头文件。

## 验证流程中发现并修正的问题

第一次审查发现候选包应在消费验收后才替换正式包，三种方案一起调整。

探索运行 comparison-v2 又暴露了上游消费测试的边界：xmltest.cpp 使用引号 include，
和源树 tinyxml2.h 相邻，实际编译依赖命中 SOURCE/TINYXML2.H。损坏解包头文件时，
A 的任务错误地成功，被预先设置的负例 oracle 拒绝；B/C 尚未运行到该场景。
共享的消费构造对三者都有同一漏洞，不能算某个后端的优势或劣势。

正式 comparison-v3 将未改断言的 xmltest.cpp 与 resources 放到隔离源码目录，
不复制 tinyxml2.h/.cpp；消费测试必须使用解包 prefix 的头文件和库。还检查两次
独立消费的 tinyxml2_DIR 均指向本次 prefix，真实编译依赖确认读取 RELOCATED/INCLUDE
中的头文件。测试输出目录新建，避免复用旧测试输出。

runner 原型注册产物时也曾重新接受当前 hash，审查后改为校验生产者原 hash；
错误和缺失产物成为记录中的失败。另有 3 个聚焦回归检查错误 hash、缺失产物和
消费前漂移，均通过。这些开发修正不混入正式方案效果统计。

沙箱中的 MSBuild 子进程曾停滞，已核对并清理仅本次启动的进程树，正式比较在
正常本机进程环境执行。该环境试验不计入方案运行速度或 runner 能力。

## 实际调用与成本

计时只覆盖任务执行，独立 oracle 成本另外记录；不含资料准备、原型开发、故障
定位和模型推理。外部命令数是 harness 直接发起的命令，不包含 MSBuild/compiler
内部进程。Python 动作账本与命令数分开，不合成为一个假定工作量。

| 观测量 | A | B | C |
| --- | ---: | ---: | ---: |
| 正常任务执行秒数 | 16.90 | 16.75 | 16.86 |
| 4 次暖缓存成功运行的中位秒数 | 9.11 | 9.23 | 9.21 |
| 成功任务的外部命令数 | 8 | 9 | 9 |
| 每次成功的额外 oracle 命令数 | 3 | 3 | 3 |
| 正常任务额外 oracle 秒数 | 8.16 | 8.15 | 8.14 |
| 正常任务捕获的命令输出字节 | 4,523 | 9,030 | 9,030 |
| runner 额外产物 hash 检查次数 | 0 | 0 | 4 |
| 实际 XML 修复编辑次数 | 1 | 1 | 1 |
| 修复场景新 attempt 完整重跑次数 | 3 | 3 | 3 |

每个任务三者都是一次可复用 recipe 调用。C 没有减少模型必须发起的命令数量，
本轮也没有实际模型实验。命令输出主要保存在证据文件里，字节数不是 token 消耗。
单次时间差不足以判断速度优劣。

XML 修复是实际文本恢复；archive/consumer 的修复是采用干净新路径/新解包，
未修复旧失败目录，也没有 resume。三者都重跑完整配方，成功时各执行 8/9/9 个
外部命令，再承担相同的第二次独立消费验收。故障定位与人工决策时间未测量，
不能把场景名称硬计为一次自动恢复。

独立 oracle 重新读最终 tar，对照本次 install 的成员与内容，再到第二个新 prefix
重新编译运行消费测试。成本约 8 秒和 3 个命令，是实验额外验证，不要求正常
产品使用无条件重复两遍所有业务测试。

## 复杂度与收益归属

| 内容 | 本原型规模或职责 | 归属 |
| --- | --- | --- |
| 上游构建、测试、安装与消费测试 | 既有 CMake/CTest 流程 | 继续交给上游系统 |
| 项目任务定义 | project_steps 58 行，三者共用 | recipe 的项目知识 |
| 命令捕获 | Calls 27 行，三者共用 | 实验基础设施 |
| 失败停止与顺序编排 | imperative 17 行，A/B 共用 | 成熟项目脚本足以承接本次任务 |
| 验证打包 wrapper | pack_operation.py 258 行，含两个后端、内容核对与回执 | 共同操作契约与验证工作，不能整体归功于 ToolX |
| 最小 runner | runner.py 58 行，核心 execute 45 行 | C 的通用产物引用与逐步记录 |
| 独立结果 oracle | oracle 68 行，加隔离消费构造 | 共同验收工作 |

这些是物理行数和职责划分，含注释，不是最小实现下界，也不意味着完整生产
runner 只需要 58 行。C 的增量日志未测试 crash consistency、中断恢复、进程树
隔离或并发；不能把它称为可靠恢复账本。

B/C 共用的 ToolX 后端仍需要 Python 内容核对和失败回执，未减掉这些额外验证。
ToolX 的两个进程替代成熟后端的 copytree 加一个 tar 命令，当前没有结果优势。
SDK 的 install tree 已基本具备交付布局，A 为对齐操作契约也执行了 copytree；
实际成熟 recipe 可以省略这次复制。这项限制有利于给予 ToolX 机会，不支持
宣称它减少了任务复杂度；未跑的优化不计入计时结果。

C 多解决的是集中表达依赖、集中检查身份、增量查看步骤；B 已在少数明确消费点
检查当前包 hash 并返回准确阶段状态。本任务没有发现 B 反复卡在跨步骤关联、
错误传递或验收一致性上，也没有测得 C 的额外修复收益。未来多个独立任务也许
会产生复用需求，本轮不作泛化断言。

## 产物与复现

正式输出目录是 `temp/v04-slice-20261018/comparison-v3`，包括：

- environment.json、predeclared.json、代码快照和完整 SHA-256；
- summary.json、comparison.json 和逐场景 metrics.csv；
- 各运行 input-manifest、实际 argv/cwd/exit、stdout/stderr、package receipt；
- C 的 ledger、失败 stage、候选包与隔离消费目录；
- A/B/C 的真实 `release/tinyxml2-sdk.tar` 和消费测试 executable；
- evidence.zip，约 2.96 MB，包含便携证据、三份最终 SDK、代码与项目资料，省略构建缓存。

三份最终 tar 大小为 454,144 / 453,632 / 453,632 字节，均通过内容与消费检查。
不同 tar 后端元数据、每个方案不同的编译路径会影响 bytes/hash，不要求三包逐字节
相同；每个包的身份、成员内容和本次安装树独立关联。

原型和重跑方法位于[实验目录说明](../../../experiments/v04_slice/README.md)。
生成数据放在忽略目录，仓库报告不依赖本机生成文件存在才能通过文档检查。

## 对规划的调整

1. 把“成熟脚本、薄操作、最小核心”的比较列为架构选择门槛，准备阶段可以推翻核心。
2. 目前保留项目脚本编排和成熟工具；先研究可复用流程以及单操作真正缺少的保证。
3. 现有 JSON、非法输入、失败报告等可靠性问题可以独立修复，不需要先建设 runner。
4. 本轮不承诺四个公开命令、统一产品发行或 SDK 退役，不发布本原型协议。
5. 下一次只有出现可复现的跨步骤重复状态逻辑或修复困难，才重新比较统一核心。

对应[主线设计](../design/v0.4.x-mainline.md)已改为条件方案。当前证据支持流程研究
与轻量操作方向，尚不支持把新架构作为收益来源。
