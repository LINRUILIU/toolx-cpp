# ToolX 维护收口与 v0.4 立项条件

> Audience: ToolX 维护者与后续实现者
> Status: Current decision; v0.4 product not admitted
> Applies to: v0.3.3 维护发布与尚待证据的 v0.4 方向
> Source of truth for: 本轮版本定位、职责取舍、产品准入与停止扩张条件

## 当前决定

本轮按 **v0.3.3 维护发布**推进。已有契约缺陷按风险修复，能力资料与短 recipe
随现有产品维护；不再承诺为 v0.4.0、v0.4.1 的产品阶段。发行状态与
兼容迁移以[发行说明](../../releases/v0.3.3.md)和公开规范为准。

降低 AI 完成实际自动化任务时的采用与信任成本仍是方向，但当前证据没有证明
ToolX 比成熟工具或可复用脚本明显省事。不为版本号补造新能力，不预设 runner、
统一任务协议、配置解释、已验字节发布或新 SDK。找不到值得接管的重复职责时，
就继续维护，不启动新的 minor 产品线。

本文件保留原研究路径，使历史审计链接继续有效。调研基线 24466b2、原版本名、
观察二进制、逐轮 manifest/zip 与审计正文不重标；它们不是本次维护发行的新验证。
当前版本定位覆盖早先的分版本交付设想。

## 证据如何改变选择

| 已完成切片 | 实际比较 | 结论 |
| --- | --- | --- |
| [TinyXML2 交付任务](../audits/v0.4-task-slice.md) | 成熟 recipe、薄 ToolX、最小 runner，各 9 场景 | 同等正确性；runner 未减少修复或重跑，薄打包未优于成熟路径 |
| [podkop/sing-box 配置任务](../audits/v0.4-config-slice.md) | 原生 merge、deepmerge/jsonschema、薄 ToolX，各 13 场景 | 39/39 独立验收通过；关键保护来自共同 recipe，未建立 ToolX 独特收益 |
| [首轮 AI 使用观察](../audits/v0.4-ai-observation.md) | 两个新上下文，ToolX 可选 | 均正确完成；ToolX 尝试仍增加 shadow merge，信任成本下降未证实 |
| [Caddy AI 使用观察](../audits/v0.4-caddy-ai-observation.md) | 成熟工具、可选修复版、可选旧版三个有效条件；隔离失效尝试另存 | 三者独立验收通过且均未调用 ToolX，修复版核验与修复收益未测得 |

原生 check 不等于启动验收、候选身份必须绑定、旧产物不能冒充成功等发现对成熟
方案同样有效，收益归项目流程研究。修复错误成功、错误 trace 和路径可见性是
既有正确性责任，不能自动算作竞争优势。输出统一 JSON 或预写完整项目流程，
同样不足以证明模型应采用 ToolX。

## v0.3.3 的维护范围与兼容成本

本轮保留十三个导出库与六个 CLI，修复归入现有产品：

- cfgx 最终 layer trace、追加下标、空键、有限数字、double 往返和受检索引；
  sync 逐层应用 overlay，避免预合并复活已消失子树。
- sync 保留验证与发布失败事实，resultx 不吞失败 RunResult；fsx 区分前向结果、
  回滚尝试、完成事实、错误与恢复业务步骤计数。
- 单目标原生替换；FSXJ4 的 REPLACE/RESTORED、绝对路径、witness 和恢复重试；
  以及 journal/目标、日志/实际归档/受保护路径的初始化前隔离。
- [短自动化入口](../../automation.md)说明工具、原生验收和项目发布的职责边界；
  资料改善未证明提高采用率，不作为新产品能力。

实现与逐轮证据见[契约记录](../audits/v0.4-contract-update.md)。历史门禁、底层
权限 skip、初次失败和重跑保持原样。本次维护发行另收集最终提交的证据，不用旧候选的
44/44 或 43/43 代替当前检查。

0.3.x 允许有测试、变更说明和迁移指引的正确性例外，不承诺零行为变化。JSON
保持 schema_version=1，加字段遵守加法规则；纠正旧 trace、overlay、数字文本或
rolled_back 等语义须单列，不能笼统声称旧字段含义均未变。

J4 新 writer 由新 reader 兼容读取 J1–3，但旧工具拒绝 J4。恢复前保留 producer、
journal 和原位置 witness/staging；旧相对 J1–3 从原 cwd 恢复。两份内容 witness
增加磁盘/I/O。Windows 替换依赖系统/文件系统支持和读者 delete sharing，不支持
时失败，不回退到两次 rename。完整边界见 [fsx 指南](../../modules/fsx.md)。

非法数字、不可行索引与危险路径的拒绝会改变旧调用。启用日志时，即便分离的
dangling journal 或 Windows stream 也可能拒绝，必须给出迁移方式。默认构建、
依赖和 TLS 选择不因本轮维护改变。

## 职责分配

| 职责 | 当前归属 | 重新讨论 ToolX 接管的条件 |
| --- | --- | --- |
| 通用分层和明确数组策略 | 可选薄 ToolX 或成熟 merge 库 | 相同资料下减少实际接入和核验 |
| 局部字段与范围 policy | ToolX 有界子集或成熟 validator | 不用完整标准的适配成本掩盖收益 |
| 文件来源与覆盖解释 | 未准入候选 | 重复溯源成为阻碍，准确来源能消除必要工作 |
| 项目语义、regex、引用、模块初始化 | 项目原生 validator | 当前无接管理由 |
| 启动、健康请求、测试、构建 | 项目脚本、agent、CI | 反复承担难以合理复用的具体职责 |
| 已验字节、发布、reload | 短 recipe、OS/项目成熟机制 | 留出任务中显著减少可靠性代码与核验 |
| 跨步骤编排、缓存、重试、恢复 | agent 或项目自动化 | 薄方案在产物关联、失败传递或验收一致性上反复受阻 |
| 并发发布、锁、CAS、断电恢复 | 现有部署系统 | 超出现有边界，不能由静态 preflight 冒充 |

候选生成、局部 policy、原生验证、行为验收、替换和 reload 分属不同事实。
任何接口只报告实际做过的部分；写出 candidate 不等于项目或服务验收。

## v0.4 的立项门槛

先问“ToolX 多解决什么，现有系统继续负责是否更省事”，再选能力。小规模真实
AI 观察可以继续，不等待配置解释或其他预选原型。

1. 找到独立消费项目中实际重复的职责，记录接入、额外核验、诊断和修复阻碍。
   一次项目特例或工具自身缺陷不足以立项。
2. 公平比较成熟工具/可复用脚本和薄 ToolX。同样允许资料、脚本、缓存与权限，
   不只给 ToolX 预写答案；先判断一个清晰契约和短 recipe 是否已经足够。
3. 覆盖正常完成、真实失败、旧产物/部分完成。用产物与独立验收核对成本，
   不把返回 0、调用数或模型口头信任当作采用收益。
4. 在未用于设计方案的留出项目/任务复用同一能力。收益应来自重复职责减少，
   而非为第二项目另预写流程；核算实现、依赖、测试与长期兼容成本。
5. 净收益明确且显著才决定公共表面与版本。薄方案等效就保持轻量；收益主要
   来自 recipe 就继续研究流程；无收益就停在维护。准备阶段可以推翻立项。

保留资料、版本、命令、输出、产物与验收；隔离失效、失败和重做成本不静默排除。
缺完整 transcript/token 或耗时就明确缺失，不换算模型成本。小样本发现阻碍，
不宣称统计优势。

## 复杂度与下一步

新增能力没有预留名额。私有抽象需真实复用或不可替代的平台边界；新依赖比较
构建、许可、更新与平台维护；状态文件需具体生命周期和清理规则。领域差异有
实际含义时保留，不为固定模式把未执行与成功混在空字段中。

当前不建设统一入口、四公开命令、通用任务协议、operation registry、artifact DAG、
进程引擎、resume、插件、daemon、远程调度、模型 SDK、完整 JSON Schema、sandbox
或全库 Result 重写。将来若确有重复职责需要这些设施，必须重新论证，不是预留
必经后半程。

v0.3.3 以维护版本收口，兼容说明与既有发行门禁继续适用。AI 观察保留为
研究手段；未得到立项证据前，不为 v0.4 安排产品交付或新增能力。
