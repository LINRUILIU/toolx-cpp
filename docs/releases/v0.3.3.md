# ToolX v0.3.3

> Audience: ToolX users, package consumers, and release reviewers
> Status: Released
> Applies to: v0.3.3
> Source of truth for: release narrative

Release date: 2026-10-20.

This maintenance release repairs existing correctness and automation contracts.
Earlier `v0.4` research labels, observations and frozen artifacts retain their
identities and are not this release's validation.

## Highlights

- Correct final configuration-layer traces, empty-key paths, array-index bounds,
  finite-number parsing and finite-double round trips. Apply repeated sync
  overlays in command order rather than pre-merging them.
- Preserve composed context and execution facts on sync failures. Retain failed
  fsx reports through resultx; distinguish rollback attempts, completion, errors
  and restored business-step counts.
- Replace an existing regular target with one native operation. FSXJ4 adds
  checked overwrite recovery and retry with replacement/restoration records and
  private content witnesses.
- Reject conflicting journal/log paths before initialization or publication,
  including actual rotation archives, unresolved links and Windows explicit
  streams; preserve ordinary and recognized extended-drive roots.
- Reject unsupported Windows stream paths in the journal, batch and selected
  retained backup whenever journaling is enabled, independently of logging,
  before the journal header or any business step is written.
- Add an [automation guide](../automation.md) for using existing operations while
  keeping native acceptance and publication in the project recipe.

This is maintenance and usage guidance. It introduces no runner, CLI product or
configuration-explanation operation, and no measured AI-cost benefit.

## Compatibility

The documented `0.3.x` source boundary remains, with explicit safety/correctness
exceptions under [the stability policy](../stability.md). Existing command and
exit-code sets remain. JSON uses `schema_version=1`; validation, execution and
rollback facts are additive. Corrected trace, overlay and rollback facts are
visible changes, not a promise to retain incorrect historical values. Consumers
must tolerate new fields and must not classify failures by English messages.

New writers use FSXJ4; the new reader still accepts FSXJ1–3. **Older ToolX versions
reject FSXJ4.** Keep the producing version until recovery completes. Legacy J1–3
relative records must be recovered from their original working directory; an
absolute journal filename does not supply the missing origin.

Overwrite recovery retains two private old/new witness copies in addition to
the staged replacement file and restoration staging, adding disk and I/O cost. Keep
journal, targets and dependent witnesses/staging at their recorded locations
until recovery or cleanup finishes. Absolute J4 paths do not remap a relocated
tree; partial recovery retains dependent evidence.

Native replacement rejects directories and symbolic links. Windows requires
system/filesystem support for `FileRenameInfoEx` POSIX replacement semantics and
delete-sharing from readers. Unsupported or sharing-conflicting operations fail
without the old two-rename fallback, preserving the old target. Complete ACL or
platform metadata fidelity is not promised.

Other visible corrections include:

- Type-changing overlay sequences can produce different corrected output;
  traces now describe surviving values and final array indices.
- Invalid/unrepresentable JSON numbers, non-finite ranges, overflowing indices
  and impossible SetNode indices are rejected. Finite doubles may gain digits
  and a `.0` suffix to retain their type and value.
- With logging, overlap with the main log or actual archives is usage error `2`
  before writes. Unresolved symlink components, parent traversal after a missing
  component and Windows explicit streams also fail, even when otherwise separate.
- With journaling on Windows, explicit streams in journal/batch/selected-backup
  paths are rejected even without logging. In sync this is a publish error `1`,
  not usage error `2`; the API call is reported as attempted with zero completed
  steps. These previously accepted paths must migrate to ordinary separate files.
  Ordinary and recognized extended-drive roots remain valid; no-journal behavior
  and POSIX literal-colon names retain their existing boundary.

Exact contracts: [fsx](../modules/fsx.md), [cfgx](../modules/cfgx.md),
[resultx](../modules/resultx.md) and [sync](../cli/toolx-sync.md).

## Build and dependency impact

The product set remains thirteen library targets and six CLIs. C++20/CMake
requirements, dependency selection and default TLS behavior do not change.
Default builds and binary packages select no TLS backend; OpenSSL and mbedTLS
remain optional and mutually exclusive. Source compatibility does not promise
ABI compatibility across toolchains or build configurations.

Source packaging excludes generated runtime/test-fixture roots and Python
bytecode/caches. The archive checker rejects those entries while retaining
experiment scripts, recipes and the documented showcase log fixture.

Release verification covers the exact tagged source, build, install, archive
and platform results. Historical passes, permission skips and retries remain in
the [contract record](../development/audits/v0.4-contract-update.md) under their
original identities and do not substitute for current release evidence.

## Migration

1. Upgrade writers and recovery tools together; retain the producer while its J4
   journals may need recovery. Recover relative J1–3 in the original cwd. Do not
   edit headers to force another version to accept a journal.
2. Reserve witness space and preserve recorded locations until cleanup/recovery
   completes. Check Windows replacement support and reader sharing.
3. Separate logs/archives from inputs, outputs and journals. With logging, use
   valid existing link targets, avoid traversal after missing directories and
   replace explicit Windows streams with ordinary paths. Journaled Windows batch,
   journal and selected-backup paths also require ordinary files independently
   of logging; omitting a log file does not restore the old stream acceptance.
4. Review type-changing overlay expectations and double-text golden files.
   Handle additive JSON facts and inspect rollback attempt/completion separately.
5. Keep native validation, live service checks and publication of the exact
   accepted bytes in the project recipe. A new sync invocation re-reads inputs;
   it is not a checked-bytes publication API.

## Known limitations

- No multi-file transaction, concurrent-writer/CAS guarantee, adversarial path
  sandbox, complete ACL fidelity or universal sudden-power-loss guarantee.
- Layer trace is not file-level provenance or override history; schemax is a
  bounded subset, not full JSON Schema.
- Programmatically supplied non-finite cfgx nodes require caller rejection before
  `ToJson`; finite-double round trips do not cover NaN/Infinity.
- Snapshot copies new resolved content rather than backing up the old output;
  dry-run does not bind a later publish or prove output writability.
- CI verification is limited to the exercised platforms and configurations;
  a privilege-dependent skip is not an executed pass. The optional mbedTLS
  backend remains outside the current CI matrix.
- Real observations have not established lower AI adoption, extra verification
  or repair costs. Future `v0.4` work needs repeated real duties, a mature baseline
  and held-out material net benefit; maintenance can continue without a new line.
